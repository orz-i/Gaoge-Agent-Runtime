# ADR 0011 — ModelInvocation Physical Dispatch Claim and Retry Eligibility

- **Status:** Accepted for the local governance branch `governance/model-invocation`; merge and release are separate gates, 2026-10-23.
- **Scope:** Direct Agent `ModelInvocation` claim, final physical Provider dispatch, and durable `RetryAfter` across all Agent Runner configurations.
- **Compatibility:** **BREAKING** for pre-stable Beta direct Agent retries. There is no old immediate-Resume bridge and no silent migration of released pending invocations lacking `RetryAfter`.
- **Not changed:** Kernel six-state Run lifecycle, Store SQL/SQLite schema, Provider wire APIs, separate Tool execution semantics, and the Agent-owned pending/completed/consumed invocation states.

## Problem

A `ModelInvocation` claim was committed **before** entering the Runner's model concurrency limiter and `ModelMiddleware`. Waiting there could outlive the invocation's own `ExecutionLeaseUntil`. A second worker could then claim, deliver and complete the same logical invocation, while the former worker retained an in-memory request. Its old pre-provider checks did not reload the current claim; it could still deliver a second physical Provider request. A deterministic clock/blocked-middleware reproduction observed **two Provider deliveries with the same Invocation ID**.

Separately, the prior `releaseModelInvocationExecution` wrote a persisted `RetryAfter` only when the Runner enabled `RunExecution`. Direct non-native `Resume` could bypass the emitted wakeup time and immediately re-dispatch retryable requests. That was a compatibility branch, not a deliberate execution contract.

## Decision

1. Retain the existing Agent `ModelInvocation` and `Kernel.Runtime` ownership. No extra lease table, scheduler, status, or alternate authority.
2. Before a **physical** Provider call, and **after all Model Middleware and concurrency admission**, validate the currently persisted Run. Require the Run to remain `running` and the committed Revision to match the successfully claimed snapshot. Kernel CAS guarantees that an Invocation ID, RequestHash, attempt, or lease takeover cannot change without incrementing that Revision, so the final guard does **not** need to deserialize the entire Agent state again. It separately checks the originally committed pending claim and unexpired local `ExecutionLeaseUntil`. Also enforce the existing Run execution epoch and current Tool/Catalog declaration check at this boundary. Reject invalid or stale ownership before sending the request. One additional Store load occurs per actual physical Provider call; this is deliberate but requires profiling on large Agent states.
3. Model middleware can observe, reserve budgets or block. It cannot promote an expired claim into physical dispatch. A failed **pre-provider admission guard** is distinguishable from a failure returned by `model.Client`: no Provider was called, so it cannot be charged as a Model receipt or consume physical retries. An expired/stolen Claim (`ErrModelInvocationBusy` or CAS conflict) leaves a recoverable pending Run. A **permanent frozen-request contract violation** (`ErrInvalidRequest` from the Agent final boundary) instead terminates the Run with `agent.model_dispatch_invalid`; it must not leave a poisoned Run retrying forever. In contrast, a Provider that itself returns a similar error is still treated as a genuine Provider failure.
4. Every retryable Model failure releases its claim and persists **the same** deterministic `RetryAfter` alongside its `agent.model_invocation.retryable` wakeup, whether or not `RunExecution` is enabled. `Resume` checks `RetryAfter` **before** acquiring the execution owner; `claimModelInvocationExecution` also enforces the due time. Future due time returns `ErrModelInvocationBusy` without a physical Provider call or a Run Revision change.
5. A released Pending invocation with `ExecutionAttempt > 0`, no active claim and no `RetryAfter` is invalid state. Do not infer a due time, silently upgrade the old protocol, or retain immediate retries. A first unclaimed Pending invocation remains valid without RetryAfter.
6. Shared Budget may persist its own `Dispatched` reservation before the Agent's final physical dispatch. If that final boundary then **proves** there was no `model.Client` call, `agent.IsModelPreDispatchDenied` gives the trusted Harness Budget middleware a narrow signal to call `budget.Coordinator.RequeueProvenUnsent`. That ledger operation checks the *exact* revision returned by its earlier `Dispatch`, plus the held/active/not-settled reservation, then moves it back to a waiting (un-dispatched) state with the same logical request hash and budget estimate. A fresh Agent Claim can subsequently re-admit the same Invocation ID. When a newer worker or any unrelated ledger writer has advanced the revision, or the original result is uncertain, reversal is **rejected** and the prior quota remains conservative. A Provider error with identical text/type does **not** supply Agent's private no-send proof. This is not a generic refund mechanism for unknown physical calls.
7. Remove `BudgetMiddleware.ModelWithPrepare` entirely. The API permitted a second post-intent model-input projection after quota reservation, contradicting ADR 0010's single `PrepareModelRequest` boundary. Budget `Model` now handles only admitted, already-prepared invocations; a pre-intent projection error occurs **before** shared-budget reservation or physical dispatch. Delete the associated compatibility tests and replace them with real Agent pre-intent rejection and Shared Budget tests. There is no compatibility wrapper.

## Non-guarantees

- This fences stale work **before** Provider dispatch; there is still a finite race window between the final Store check and the remote network write. It does not promise physically exactly-once delivery.
- A Provider may finish late or ignore cancellation after dispatch. A crash after upstream success but before receipt commit remains an uncertain outcome, subject to existing at-least-once and reconciliation rules. Integrators must not assume the underlying model API implements idempotent requests merely because the SDK passes a stable Invocation ID.
- A Host-supplied `ModelMiddleware` is trusted execution code. It may have its own effects; the Agent fence governs the actual `model.Client` dispatch through its normal chain, not arbitrary I/O a Host performs outside it.
- The Shared Budget no-send requeue is deliberately **fail-closed** when its ledger has changed since Dispatch, including unrelated concurrent budget updates. In that case an operator may need to reconcile a conservative unknown reservation, rather than risking refund of a later physical send.
- The Feature `RetryAfter` uses the configured Agent Clock, as in existing native execution. Store-execution epoch/lease checks still use Store authority. Cross-worker clock skew and long external calls remain deployment concerns rather than grounds for a second scheduling subsystem.

## Migration and verification

- Drain or explicitly reconcile all old pre-stable Beta Pending Model attempts that have been released without `RetryAfter`; this runtime does not reconstruct their timing or automatically replay them. Keep already committed terminal receipts as historical data.
- A newly delivered retryable error never creates an immediate-retry shortcut in direct Agent or native `RunExecution` paths. Hosts must honor the returned persisted wakeup/due time rather than loop on `Resume` before it.
- Hosts using `BudgetMiddleware.ModelWithPrepare` must move the projection to `agent.Dependencies.PrepareModelRequest` and call the standard `BudgetMiddleware.Model` through the Model middleware chain. Pre-intent failures never create a shared-budget reservation.
- Regression: simulate a former worker blocked in middleware, claim lease expiry, second-worker takeover/completion, and former-worker resumption. Exactly one physical request is delivered in this deterministic race. Separately hold the shared model limiter past a claim's deadline without takeover; the waiting request cannot dispatch or terminalize its Run, and a subsequent fresh Claim can complete that Run. Repeat with a slow provider-hosted Tool Catalog resolution during the final preflight, where an additional worker takes ownership; the stale worker must still be fenced. Verify direct/native Resume before and after RetryAfter, old released Pending rejection, original request/receipt stability, and full Agent/Store test suites.
- Shared Budget regression: hold downstream middleware after budget Dispatch, expire its Claim before the Provider is called, then assert the uncertain reservation is requeued and the same logical Invocation can be successfully re-admitted. Verify that a Provider returning an identical error stays an unknown physical outcome; test the ledger revision fence against a newer Dispatch and unrelated concurrent updates.
- Release gate: test/race/lint/consumer checks, benchmark evidence for the extra Store preflight, and real PostgreSQL/Redis integration where available. Publish in a **new** Beta; do not alter an existing tagged release.

### Memory benchmark baseline (Apple M4, Go workspace)

For `BenchmarkAgentDeterministicLoopMemory` at 200 iterations/sample, prior `main@9c558b3` reported roughly **42.2 KiB** allocated and **208 allocs/op**; the optimized final Store-Revision fence reported roughly **44.4 KiB** and **213 allocs/op**. Wall time fluctuated across short runs (~34–47 µs in the candidate), so these small samples do **not** certify a stable latency delta. An initial implementation that decoded the entire state after loading incurred about **46.5 KiB / 224 allocs/op**, and was removed. Long-session 10/50/100-turn database and p95 measurements remain a separate admission condition before claiming performance neutrality.
