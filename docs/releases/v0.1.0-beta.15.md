# Agent Runtime 0.1.0-beta.15

Beta.15 adds **optional, bounded automatic execution segments** to the durable direct-Agent call allowance introduced in Beta.14. It does not introduce an unlimited execution budget or automatically enable renewals in consuming hosts.

## Problem and behavior

Beta.14 pauses a direct Agent at a soft model/tool-call allowance boundary and needs an explicitly authorized user grant to continue. A long task can hit several such boundaries even while remaining below its immutable hard ceiling. Beta.15 lets a trusted host opt a *new direct Agent Run* into a frozen automatic-renewal policy so that bounded work continues on the original Run, with the existing human continuation path used if autonomous renewals are exhausted or a no-progress threshold is reached.

## SDK changes

- Add optional `agent.StartRequest.AutoAllowance` and `harness.StartRequest.AutoAllowance`. The `agent.AutoAllowancePolicy` contains `ModelStep`, `ToolStep`, `MaxModelRenewals`, `MaxToolRenewals`, and `MaxNoProgressWindow`. Each enabled dimension must have an initial positive `CallAllowance`. Policy is validated **before dispatch** and stored with Agent state, never created from a model/tool output.
- Before a new logical model invocation or next queued local Tool, persist one bounded cumulative allowance increment under Kernel revision CAS, with durable delayed `agent.allowance_auto_granted` wakeup. For hosted Runs, the direct Runner yields at the boundary; the existing Continuation Scheduler/Worker resumes the same Run. Completed Tool results and model receipts are not replayed.
- Independently cap each dimension's automatic-renewal count and truncate steps to the **original immutable per-Run absolute hard limits**. At the hard ceiling, normal terminal limit semantics still apply.
- Conservatively stop automatic grants when a fingerprint of the last *settled* work repeats across configured segments. The fingerprint ignores transient Tool IDs, canonicalizes JSON arguments without losing large-integer precision, and preserves meaningful output whitespace. It is private to persisted Agent state and never included in public event payloads.
- Provide brief, ephemeral model guidance near an automatic segment boundary; the guidance is not a durable transcript entry, new authorization, Context compactor or capability setting.
- Add deterministic tests for same-Run multi-segment completion, queued Tool batch without replay, manual fallback, invalid/oversized policies, approval/cancellation, concurrent Worker CAS, actual SQL-store restart, Harness Context checkpoint stability and Kernel Outbox → Scheduler → Worker recovery.

## Host migration and compatibility

1. Upgrade **all nine Go modules** together to `v0.1.0-beta.15`. The TypeScript client archive is `orz-i-agent-runtime-client-0.1.0-beta.15.tgz`, attached to the GitHub prerelease. No npm publication.
2. Existing Beta.14 `StartRequest.CallAllowance`, `GrantCallAllowance`, `paused_budget`, HTTP owner authorization, Turn Feed and TypeScript API are unchanged. **No automatic policy provided = exact Beta.14 manual continuation.** There are no new HTTP endpoints or OpenAPI changes.
3. Hosts may supply `AutoAllowance` only when creating a new **direct Agent** Harness Turn. Team, GroupChat, Workflow and child Feature invocations do not inherit this opt-in and cannot silently expand per-feature budgets.
4. Disabled or exhausted auto renewal falls back to an owner-authorized Beta.14 manual grant when below absolute hard limits. Waiting approval, cancellation, deadline, unknown external writes, provider retry failures, Context Window hard guards, shared Turn budgets and terminal Runs are not auto-grantable.
5. P2 policy/counters are persisted in a new optional JSON field on Agent Run state. No SQL migration is required; existing Beta.14 Runs without that field continue in manual mode. Do not deploy mixed-version workers against P2 Runs or downgrade active P2 Runs directly to Beta.14. Drain workers or stop opting in new Runs before a coordinated downgrade.
6. Host must deliberately enforce configuration and rollout limits and review effect on actual provider costs/latency. Repeated work is a conservative heuristic, not proof of lack of semantic progress; manual intervention remains available.

## Verification and limitations

The candidate passed `GOTOOLCHAIN=go1.27.2 make beta`, including Go fmt/tidy/vet/tests/race/lint/coverage, TypeScript tests/typecheck/build, vulnerability audit, packed clean consumers, real PostgreSQL/Redis integrations, and OTel Collector E2E. Verify the **tagged** release again in protected CI, confirm all ten root/module tags match the accepted SHA, and inspect attached TypeScript archive before adopting it.

The P2-specific SQL restart regression used the production GORM adapter against SQLite; it did not simulate a paid-model provider or actual multi-process production PostgreSQL crash. The general Beta integration suite covers real PostgreSQL and Redis. An adopting host must separately validate its own Chat/Context/Approval/connection-recovery behavior.

## Release decision

Publish only after protected-branch PR checks and the immutable Beta tag/release workflow both pass. Never retag Beta.14; no automatic Gaoge host pin adoption as part of this SDK release.
