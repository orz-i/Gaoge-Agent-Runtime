## Correctness invariants

1. **Dataset identity:** exact suite ID, group membership, source bytes, task instructions, tool policy, Context profile and Oracle are tied to the task version and SHA-256 dataset hash. New suite has five groups × eight unique cases. Original two-case corpus and its hashing inputs are unchanged. Other model IDs within the same Provider do not silently alter dataset identity.
2. **No false positive quality:** a sample passes only if the real evidence and draft Oracle, non-replayed Tool receipts, stable Run/Turn ownership and required recovery checks pass. Scripted Model success is tagged `scripted_oracle_calibration`, never real-model performance.
3. **No sample-count confusion:** the quality report protocol expects exactly `40 × repetitions`, checks every sampled CaseID against the fixed corpus and rejects repeated `(caseID, repetition)` pairs. Quality repetition is bounded to 1–3; legacy retains 1–20.
4. **No invented tokens/cost:** reported Provider usage remains known/unknown by individual receipt. The group Token figure is unknown unless *all* relevant calls have complete usage. Probe usage and paid task usage stay separate. No dollars are inferred from token counts without Host price authority.
5. **No hidden execution:** real-model work is interactive, explicit and needs Host-selected endpoint/model/capability, current build and newly hidden API key. Unknown model capabilities still fail the existing preflight. No unattended calls or background jobs are started.
6. **No misleading comparison:** different dataset hash, suite, profile, task version, output budget or repetition number block numerical comparison. Incomplete results remain explicitly partial and never grant an improvement/ranking conclusion.
7. **No alternate durability:** existing same-Run recovery checks, lease fencing, no-effect and committed Tool receipt policies are reused; quality cases never add execution state.

## Third live preflight: overstrict SDK ciphertext equality invariant

The user's subsequent official OpenAI Responses preflight at 4,096 max output tokens yielded the same completed `baseline_probe_echo` and final response; the **new structured observation** reported `reasoningDone=true`, `encryptedDone=true`, `terminalSeen=true`, `doneFinalMatch=false`. The response's status and complete Tool arguments were consistent, but the Provider still failed at the first SSE call and all 40 quality tasks remained skipped. This establishes **different opaque ciphertext strings** in done/final, not that their underlying reasoning differs.

A current OpenAI API reference explicitly instructs consumers to use the completed reasoning item and its `encrypted_content` from `response.output_item.done` for stateless continuation; it does **not** require identical encrypted bytes in the later `response.completed` projection. See https://developers.openai.com/api/reference/resources/responses/streaming-events. The existing SDK was overconstraining opaque encrypted bytes to equality while already treating done as authoritative if final omitted them. A pre-fix Go test reproduced the false rejection (`invalid provider protocol response`), then the smallest production correction allowed done to provide the replay bytes even when final's ciphertext differs. **Only the encrypted field is replaced** after strict same-index/ID, non-encrypted reasoning content, output status, Tool ID/arguments and response owner validation. A `response.output_item.added` item that already asserts completed status remains independently immutable and cannot be substituted by a conflicting done/final event.

New tests verify the correct done ciphertext survives into a second stateless Tool request and never uses the partial added or alternate final value, including a 13-event SSE reproduction matching the observed event lifecycle. Mismatched reasoning summary, Tool arguments/identity and explicit completed-added ciphertext remain invalid. The prior `different-encryption` negative fixture was superseded by this positive authoritative-done replay test, not by a blanket error suppression. The informational-only report remains privacy-safe but must not describe a differing ciphertext as a physical protocol contradiction. **At this stage, live Provider continuation had not yet been rerun with the patch; the subsequent verified result is recorded below.**

## Independent-style boundary review and preflight-only gate

A read-only review pass of the changed OpenAI Provider trust boundary was performed separately from the patch-writing sequence, based on the following invariants: (1) `added` establishes immutable item/index/Call ownership and a `status=completed` addition supplies binding terminal evidence, (2) `done` must match item owner, non-encrypted reasoning fields, and completed Tool arguments, (3) only completed-done ciphertext may replace later final reasoning ciphertext, never uncompleted added ciphertext, (4) terminal `response.completed` still needs the same response ID and valid completed status/Usage, and (5) no local Tool may run until the entire admitted output and ProviderReplay have passed reconciliation. These were checked against the current `stream_replay.go`, `client.go`, `stream_replay_test.go`, `stream_completed_added_test.go`, and new `stream_done_cipher_authority_test.go` positive/negative cases, including 13-event SSE reproduction and exact ciphertext reuse in the second request.
