# 2026-11-07 — Context Artifact candidate retrieval: narrow remediation

## Evidence and purpose

The first complete official-OpenAI `gpt-5.6-terra` `evidence-40-v1` run attempted 40 cases, with **37 passed and 3 failed** (all failures within `distractor`). Its original private JSON report, `20261107T093913Z-12da49b7.json`, has SHA-256 `562c1115541379df1d027faba6f5e74078fa46cb3dbb32a1c259f0009131db03`. This report is **preserved unchanged**; 37/40 remains the actual real-model baseline. The sample-level observed failures were: `distractor-01` (5 Context reads, no draft, `task_did_not_reach_interruption`), `distractor-05` (7 reads, no draft, `context_budget_exceeded`), and `distractor-07` (6 reads, no draft, `context_budget_exceeded`). Last captured queries were `deployment`, `RELEASE`, and `deploymentCode`, respectively; none was the precise target `RELEASE R-17`. The latter two errors were *local Context admission rejections*, not Provider HTTP rejections. The first wrapper does not prove a specific underlying error.

The existing `read_context_artifact` Tool originally returned only the **first case-sensitive literal match** or a no-match. With similar records, broad queries expose a decoy first; case/field naming differences produce empty results. Repeating the same query without advancing its cursor just revisits the first match. The Tool API provided no compact, explicit list of alternatives. The resulting repeated reads consume Model invocations, Tool calls, opaque replay Context budget, and time.

## Design — optional general Tool capability, not a benchmark answer shortcut

- **Ordinary reader unchanged:** `ContextArtifactToolRegistration`, its original schema, its `harness-v1` Tool policy, case-sensitive single-literal search, existing error semantics, and byte-exact artifact content remain the default. The historical two-case baseline's fixed dataset hash `sha256:e4a782b32d69f7d7e7d25df60ef3416b4c950315e30d5cf716cd05fe2e0c4203` is pinned unchanged.
- **Explicit Host opt-in:** `ContextArtifactCandidateToolRegistration` opts into the same read-only ToolKey with a separately defined schema, and a distinct `harness-candidate-search-v1` Tool-policy identity. **Candidate navigation is automatic whenever a query is supplied to the enhanced registration**, whether or not the Model sets the optional `candidates` field. The default handler explicitly rejects `candidates=true`. Only the quality suite in the demonstration Host selects this alternate registration and instructions; no Agent Loop, routing/intent layer, Provider, Kernel, execution epoch or persistence protocol changes.
- **Literal candidates:** If the user's query has multiple exact occurrences, the Tool returns at most **three** bounded previews with an exact original-Unicode-rune offset and a `moreMatches` indicator; the content itself is not redundantly included. The Model must choose and re-read the correct original offset. A subsequent search with `nextOffset` can discover later matches instead of looping on the first; the same forward-only cursor applies to normalized hints when additional candidates exist.
- **Nonliteral hints, not authority:** If no exact match exists, optional simple Unicode lowercasing and separator normalization can propose a small set of candidate offsets under `searchMode=normalized_hints`. **`found` remains false and `content` remains empty.** Hints never assert literal/evidence correctness. A real `read_context_artifact` query against original bytes is still required to return facts. No model-generated answer, deployment code, date/window, or target release is substituted by the Tool.
- **Bounded outputs and isolation:** Candidate previews are capped at three × 35 runes and the serialized candidate response is additionally bounded to **512 bytes** including metadata, with Unicode-safe truncation. Authorization remains the original Run→Turn→Session/artifact identity and content hash checks; cross-session artifacts are still forbidden. No new public artifact enumeration or bypass of ToolKey approval is introduced. Default reader performs its original single search without candidate indexing or result expansion.
- **Correctness protocol:** Candidate offsets point to the start of the preview in the *original*, exact source. Previews recognize both raw and JSON-escaped newlines, preventing the previous log line from hiding a requested record label. Original source bytes, stored artifact IDs and hashes remain immutable; model-visible candidate previews are not credited by the Oracle as an exact evidence read.

## Exit criteria and remaining risks

Do **not** call this repair a real-model 40/40 success. No new paid Provider sample has been executed. The Tool is still driven by model-chosen queries and offsets; although candidate discovery no longer requires the Model to supply a flag, a Model that ignores the candidate list or selects the wrong record may still fail. An exact query that matches a single wrong record is not automatically corrected. The safe Tool does not rank or authorize a preferred record and never relaxes the fail-closed Context/token limit. The `task_did_not_reach_interruption` wrapper remains insufficient for fully attributing one historical failure. The first real 40-case score requires a distinct explicit retest with a new model budget, report and newly selected quality profile; do not retrospectively rewrite the first report.

Merge requires independent diff review, Go test/race/vet/lint, Python report compatibility, release clean-consumer gates, and GitHub CI on the actual final PR Head. The earlier doc-only PR #95 is separate from this runtime Tool enhancement.
