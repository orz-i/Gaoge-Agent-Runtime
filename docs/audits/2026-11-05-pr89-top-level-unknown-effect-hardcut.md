## Shared immutable physical-outcome boundary

1. `withPhysicalInvocationDispatch` remains authoritative for the actual physical effect: a Feature returning **no Run** and no private no-effect proof retains its durable dispatch grant and returns `ErrExecutionOutcomeUnknown`, including for a generic, wrapped Kernel CAS conflict, a plain error, or a nil callback error.
2. `finishTopLevelStart` must **not erase** that unknown-effect result merely because `Refresh` sees a matching local Cancelled Run. Only an original first-attempt Agent with a **pre-dispatch** Kernel conflict, no unknown-effect receipt, and no unresolved physical dispatch may attempt this narrow idempotent cancellation reconciliation. A synthetic pre-grant conflict can still be converged by a later Refresh if the first projection CAS loses its acknowledgment.
3. `syncRuntimeSnapshotWithCancellationProof` checks the unresolved physical dispatch ledger before projecting any ordinary top-level **terminal** Run snapshot, regardless of whether the caller is Start, Refresh, replay or retry. The check is restricted to terminal Run observations: a legitimate nonterminal Run may remain visible as running while work progresses. With pending uncertain effects the method fails closed using `ErrExecutionOutcomeUnknown` instead of committing a fabricated Completed/Failed/Cancelled Turn.
4. `verifiedCancellation=true` is reserved for the existing **proven Cancel** path after descendant and delegation reconciliation, not a way for ordinary Refresh or Feature Start to ignore a stale grant. Existing durable Cancel intent, native Kernel CAS, Handoff routing and multi-Run cleanup remain mandatory. A missing Feature receipt cannot be converted to a no-effect or no-charge accounting fact.
5. Valid no-effect certificates preserve the preexisting failed-admission terminal path; they do not create a new physical Run. Outcome classifications are grounded in the dispatch grant, never inferred from an unrelated local Run or solely from a `kernel.ErrConflict` error.

## Boundary and residual risks

- A custom Feature adapter that invents a Store write ACK, a physical native Run identity or completely fabricated terminal state is outside the trusted Store/Feature receipt contract; the Harness maintains the existing fail-closed unknown-effect behavior where it has insufficient evidence.
- Existing independent merge audit also identified an out-of-contract malicious custom Store which can write an owner different from its `CreateSession`/`CreateTurn` success return. It reproduces on the pre-PR `main` baseline and is explicitly **not claimed fixed** here. The Store remains the authority for transactional CAS and durable identity; supporting Byzantine Stores would require a separate architectural trust-model change.
- `OpenTelemetry Collector E2E` runs only on `push` events and is skipped in pull request CI. Live third-party Provider/gateway routing and billing acceptance remain distinct gates; the unchanged Provider module's local receipt/middleware/replay tests are not equivalent to a real third-party API request.
